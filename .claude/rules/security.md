# Security & Compliance

> §1.x — Auth, secrets, audit, PII. Loaded automatically by Claude Code.

## Secrets

§1.1 **Connection-string encryption is mandatory.** All data-source connection strings are encrypted at rest using `Beacon:EncryptionKey` (required config). NEVER store plaintext connection strings in the database, in entities, in tests, or in fixture files. The key is checked at startup in every environment (`EncryptionKeyRequirements`: base64 of at least 32 random bytes — not printable text, at least 16 distinct byte values — never a published value or a `${...}` placeholder; the message never contains it). A replaced key moves to `Beacon:PreviousEncryptionKeys` (decrypt only, never strength-checked, never used to encrypt); values move to the current key when next saved or through `IStoredValueReEncryptionService` (conditional writes, run as a background job — the sample host's `ReEncryptStoredValuesJob` — never inline in startup). `Beacon:Mcp:CallerHashKey` keeps MCP caller hashes stable across a key change. Never weaken the check, write with a previous key, or log a key (previous keys are logged by their position only). **Transport:** every data-source connection must authenticate the server over TLS, judged by the connector's `IDataSourceTransportInspector` (registered by its `Add{Engine}Connector()`, parsing with the driver's own builder: PostgreSQL/MySQL `VerifyFull`, SQL Server/Synapse `Encrypt` Mandatory|Strict without `TrustServerCertificate`, Snowflake no `insecureMode`/non-`ENABLED` `certRevocationCheckMode`/non-https `scheme`, API https URLs; Databricks/BigQuery/CloudWatch pass; a type without an inspector is never verified). `IDataSourceTransportPolicy` refuses a new or changed connection on create, update and test-connection (`DataSourceTransportException`, naming the option, never a value); a stored one is checked where it becomes a live string (`IDataSourceConnectionResolver`: `GetConnectionString` for database readers, `GetConnectionData` for the JSON connectors, `GetWriteConnectionString` for the migration writer only; nothing else decrypts `EncryptedConnectionData` to connect, pinned by `StoredConnectionPathTests`): one Warning per source per process, or a refusal under `Beacon:DataSources:Transport:EnforceOnExisting`; `AllowInsecure` lifts it (dev hosts only, startup Warning outside Development). Never disable certificate validation in code or docs, and a new connection path must go through the resolver or the policy. Host-managed strings are checked as stored ones (Warning, or refusal under `EnforceOnExisting`), never refused as new. **Rotation and disable:** credentials are replaced in place with `PUT /data-sources/{id}` (`UpdateDataSourceCommand`, DataSourceAdmin; a null or empty connection keeps the stored one, which is never returned; a change of engine, host, port or database, or a target the inspector cannot read, needs `confirmTargetChange` (409 otherwise) and clears the sampled column values in the same save; the old driver pool is emptied through `DbConnectionFactory.ClearPool`). A disabled source (`DataSource.DisabledTime`, `PUT /data-sources/{id}/enabled`) makes no connection: every resolver path refuses it FIRST with `DataSourceDisabledException` (generic message), before decrypting or the transport check; `ConfiguredDatabaseResolver` lets that refusal propagate like the transport one (never a cross-database verdict), and a subscription run on it is recorded failed with `NotificationFailureReasons.DataSourceDisabled`. Both are immediate (no second approval) and staged security events (`credentials_rotated`/`data_source_updated` with `targetChanged`, `data_source_disabled`/`data_source_enabled`), never a value.

§1.2 **No secrets in source.** NEVER hardcode connection strings, API keys, encryption keys, OIDC client secrets, or LLM provider keys in `.cs`, `.razor`, `.json`, or test files. All sensitive values come from `appsettings.json` (gitignored sections), environment variables, or the encrypted store.

## API keys

§1.3 **API keys are SHA256-hashed before storage.** The raw key is shown to the user exactly once at creation and never persisted in plaintext. Never log or echo the raw key.

§1.4 **Scoped keys only.** API keys carry scopes (`Read`, `Execute`, `Admin`) and optional project restrictions — enforce both on every request, not just the scope.

## MCP guardrails

§1.5 **Every SQL execution path is read-only enforced, defense-in-depth, through one gate.** `ISqlExecutionGate` (length cap → refusal of control characters other than tab/LF/CR and of every Unicode noncharacter — the parser reads U+FFFF as the end of its input → regex guardrail → dialect-aware `SqlReadOnlyAstValidator` → cross-database rule → host policy → row cap written into the SQL) → `IDataSourceProvider.ExecuteReadOnlyQueryAsync`, which on PostgreSQL runs the statement inside a `READ ONLY` transaction (plus `default_transaction_read_only`) as a batch of exactly one command (`DbBatch`, so the driver refuses a second statement and the server refuses a multi-statement Parse — never a `DbCommand` the driver would split) and on MySQL inside `START TRANSACTION READ ONLY` (plus `SET SESSION TRANSACTION READ ONLY`) on a connection with statement batches off; BigQuery and Databricks have no read-only session, so their overrides bind the connector's own verdict (dialect-correct parser + configured project/catalog) and, on BigQuery, a dry run whose statement type must be `SELECT`. The validator's dialect comes from `DataSourceSqlDialect.Of(dataSource)` (BigQuery/Databricks by data source type); an unknown or null dialect is refused, never parsed with a generic grammar. MCP call sites (`ProjectQueryTool`, `QueryExecutionService`, `CrossSourceQueryService`, `DryRunTool`, `McpEvalService`, saved-query tools) and Beacon's own features alike: previews, subscriptions, AI actor checks, migration reads and column value samplers run through `GatedSqlRunner` (read-only always on, a mandatory row cap, `Beacon:Query:MaxExecutionRows` cap, a migration read's own `Beacon:Migrations:MaxRows` — written into the SQL, also on a final query's in-memory join; on the engines the database provider serves (PostgreSQL, MySQL, SQL Server, Synapse, Snowflake) the read also stops one row past it through `IRowCappedReadOnlyExecution`, which BigQuery (it stops reading the job's pages) and Databricks (it sends that bound as the statement's `row_limit`, with a 16 MiB `byte_limit` whose cut fails the run) also implement; every `DatabaseProvider` read, capped or not, and the in-memory join's final read fail past the `Beacon:Query:MaxResultBytes` byte budget (estimated as rows arrive, never truncated); read without a cap, a BigQuery or Databricks result over the connector's 10,000 rows fails, never truncates (each BigQuery job carries `MaximumBytesBilled`: the source's own, default 10 GiB, lowered by `Beacon:DataSources:BigQuery:MaxBytesBilled`); a BigQuery job and a Databricks statement are cancelled on the warehouse when the wait ends (timeout or caller cancellation), Snowflake also runs under the session's `STATEMENT_TIMEOUT_IN_SECONDS`, and a warehouse source's stored `QueryTimeoutSeconds` is clamped by `DataSourceQueryTimeout` (≤ 900 s); a larger result fails, never truncates — `Beacon:Query:StatementTimeoutSeconds` (default 120; a subscription's own timeout may only be shorter), the caller's cancellation; a final query on the in-memory join that times out fails the run, never an empty success); data-quality rules, documentation enum discovery and value-grounding probes evaluate the gate themselves and run its `FinalSql` on the read-only path with a statement timeout; the in-memory join's final query passes the gate with `InMemoryJoin`. A query step's SQL passes `IStepSqlSaveCheck` (the gate plus a blocking column check against stored metadata) before it is stored, also when an AI actor writes it. Rows that reach recipients (subscriptions, Custom SQL rule results) are PII-masked with `PiiRowMasker` under the linked projects' strictest PII settings. `IDataSourceProvider.SupportsDatabaseReadOnlyEnforcement` reports honestly (PostgreSQL and MySQL today; SQL Server, Synapse, Snowflake, BigQuery and Databricks rely on the parser gates and a read-only login — SQL Server's read-only path runs in a transaction that is always rolled back, which undoes but does not refuse, so it stays false; a SQL Server statement that ends that transaction (checked with `@@TRANCOUNT` and a savepoint only Beacon knows) fails the run and logs `ReadOnlyTransactionEnded`, 7116; `DataSourceReadOnlyEnforcement` surfaces `false` as a data-source badge and a save/startup warning) — do not claim coverage a provider does not have; database-level read-only is defence in depth on every engine, and every data source Beacon reads needs a read-only login. The regex guardrail judges SQL with its comments removed by the dialect's tokenizer (`SqlCommentStripper`; each comment's end computed from its own text and checked against where the engine ends it, executable comments and hints kept, anything it cannot read safely judged as written), and `StoredSql.Flatten` removes line comments before flattening; the AST stage always parses the SQL as written. `SqlAst.Parse` — every parser caller — refuses control characters, Unicode noncharacters and an END that closes no CASE (the parser would stop reading there); on PostgreSQL and T-SQL a comment marker sharing a character with another (`/*/`, `*/*`) is refused; on T-SQL an unquoted alias that is a statement keyword (`SELECT 1 COMMIT`) is refused. The row cap holds whatever bound the statement sets itself: a count above the cap, `LIMIT ALL`/`NULL`, an expression, `TOP … PERCENT` or `WITH TIES` is lowered to the cap in place or wrapped in a capped derived table (`own_bound_capped`), and a T-SQL statement with a WITH clause that cannot be lowered is blocked (`uncappable_bound`). Do not add a code path that bypasses these checks, even for "trusted" sessions. What runs is the gate's own `FinalSql` (the row cap is its `MaxRows` stage, never a limit applied after it), and `SqlExecutionPathCoverageTests` pins every gate user, every provider execute/validate/cost-estimate call (counted per file) and every `IDataSourceConnectionResolver` and `DbConnectionFactory` user: a new one is reviewed and listed with its reason. A cross-database stage follows the AST validator: `SqlCrossDatabaseRule.Validate(sql, dialect, configuredDatabase)` refuses any name qualified with a database (catalog, project) other than the one the data source's connection is configured for (`IConfiguredDatabaseResolver`; none configured or unreadable → no qualifier is accepted), functions and procedures that reach other servers, files or storage, Databricks paths, statements that switch database, catalog, schema, role or user (`USE`, `SET ROLE`, `EXECUTE AS`, …) or run SQL from a string, variable or session (`EXEC @sql`, `sp_executesql`, `EXECUTE IMMEDIATE`, `PREPARE`/`EXECUTE`, string-bodied functions), and SQL it cannot parse — it runs in `ISqlExecutionGate` (verdict `cross_database`, also with read-only enforcement off; skipped only for the in-memory join, `SqlGateRequest.ForInMemoryJoin`), on query save and on step execution, and a new execution path must not skip it. It is not applied by `IDataSourceProvider.Execute*` called directly by a host, nor by the metadata extractors (fixed catalog SQL); column value samplers build their SQL only from `SqlIdentifierGuard`-validated, quoted identifiers and run it through `GatedSqlRunner`; SQL Beacon builds from catalog names quotes them per dialect (`SqlIdentifierGuard.Quote`), and names carrying quote, bracket, semicolon or control characters are not ingested (`SqlIdentifierGuard.HasUnsafeCharacters`). The same always-on stage refuses PostgreSQL `COPY … PROGRAM` / server-file `COPY`, SQL-text extension functions (`pg_background_…`, `pgr_…`) and Databricks network/stream/reflection functions. Right after it, `SqlSystemCatalogRule` (verdict `system_catalog`, same always-on scope, skipped only for the in-memory join) refuses the engine's catalog, statistics and query-history relations in every dialect, also as the table a `DESCRIBE` names: system schemas and databases (`pg_catalog`/`pg_*`, `information_schema`, T-SQL `sys`, MySQL `mysql`/`performance_schema`/`sys`, Snowflake `SNOWFLAKE`, BigQuery `INFORMATION_SCHEMA`), catalog-reserved names (PostgreSQL `pg_*` in any schema, SQL Server compatibility views unqualified or in `dbo`, BigQuery `__TABLES__`, SQLite `sqlite_*`/`pragma_*`/`dbstat`), system table functions by exact name (T-SQL `fn_dblog`, `fn_get_sql`, …; Snowflake history, `VALIDATE`, `RESULT_SCAN`, `GET_QUERY_OPERATOR_STATS`), PostgreSQL `pg_stat*`/`pg_get_*` and comment functions in any position, and an unquoted PostgreSQL `ONLY` relation (the parser reads `ONLY t` as a table named ONLY). Beacon's own catalog reads (metadata extractors, the migration writer, `DatabaseEngineVerifier`'s engine identification on create/update/test and `HostReadOnlyLoginCheck`'s startup login check) run outside the gate; do not route them through it or loosen the rule for them.

§1.15 **Every gate request carries a row-level security context.** `SqlGateRequest` and `GatedSqlRequest` take a required `RowSecurityContext` (`NotApplicable` / `Filtered` / `Denied`); the gate refuses `Denied` (`no_entitlement`) and, while it cannot write the filter into the statement, `Filtered` (`row_security_unrewritable`), whatever the other settings say, and a missing context like `Denied`. Every path that runs SQL on a source, on a request or off it, takes the context from `IRowSecurityResolver` right before the gate and never states one itself: only the in-memory join and the save-time checks (`StepSqlSaveCheck`, a Custom SQL rule on contract save), which reach no source's rows, state `NotApplicable`. `SqlExecutionPathCoverageTests` pins the resolver's users and every file that creates a context. `Beacon:RowSecurity:Enabled` is a deployment lock, off by default, and its validator refuses it at startup while row security cannot be enforced.

§1.6 **PII detection and row limits stay on.** Both are configurable per project; do not disable them in code or default config without explicit approval. MCP read-only enforcement and PII detection are pinned on by the deployment locks `Beacon:Mcp:ForceReadOnly` / `ForcePiiDetection` (default on, binding on Admins too; with `ForceReadOnly` the gate forces read-only whatever the request says), and every MCP settings change is recorded in `AppSettingHistory` (`McpSettingsChangeAudit`) — do not flip those defaults or skip the audit. A custom PII pattern that cannot be evaluated refuses the query (and marks a column as PII), never skips; a new pattern is at most 500 characters and must not use lookarounds, backreferences or atomic groups (`CustomPiiPattern`, linear-time engine).

§1.7 **Audit logging is non-optional.** Every MCP tool invocation goes through `McpAuditService`, including the error path — never short-circuit it. Learning signals (`McpSignalService`) are recorded for the SQL-carrying tools only; see §9.5. Every security-relevant action (sign-ins, identities, roles, keys, project access, data sources, delivery, settings, approvals, ownership, tasks, curation, data contracts, migration jobs) records one event in the security audit sink, the append-only `SecurityAuditEvents` table, through `ISecurityAuditRecorder`: **stage** it in the change's own unit of work (`StageAsync`, or `SaveWithEventsAsync` when the event needs generated ids) so it commits and rolls back with the change; use `RecordAsync` only where there is no unit of work (a sign-in, a refusal, a read), never to replace staging. New actions go into `SecurityAuditActions` (`{category}.{snake_past_tense}`) and the UI catalogue. Events never carry PII or secrets — ids, counts, flags and codes only via `SecurityAuditDetails` (no names, e-mails, external ids, typed sign-in names, IPs, user agents, SQL, questions, comments, tokens, destinations); people go in as `Users.Id`. Never update or delete event rows (the interceptor refuses it; only the retention purge deletes). The non-MCP **execution log** (`ManualQueryExecutionLog`, `ISqlExecutionAudit`) gets a Started row before every statement Beacon runs on a data source for its own features (`GatedSqlRunner`, documentation enum discovery, data contract rules) and is closed with `CancellationToken.None`; it records the caller as `TriggeredByUserId` (`Users.Id`, never a name or external id) and never parameter values or a database error text; `Beacon:Audit:ExecutionLog:Required` (off by default) refuses a statement whose row cannot be written. A new provider execute call writes it or is listed as exempt with its reason in `SqlExecutionPathCoverageTests`.

§1.12 **Grounding retrieval is project-scoped, and scoping is authorization.** Glossary terms, golden exemplars, learned patterns, and replay eval cases are filtered by the caller's authorized `projectId` — NOT by data source. A data source shared across projects must never leak one project's questions, SQL, or definitions into another's prompt. Any new retrieval block must thread the authorized `projectId` through and hard-filter on it.

§1.14 **Data migration is the only write path, and it is segregated.** It is off unless the host sets `Beacon:Migrations:Enabled` — a deployment lock: the endpoints are not mapped, `MigrationWritePolicy` and `MigrationService` refuse to create or run, and no data source can be marked. It writes only into a data source an Admin marked `AllowMigrationWrites` (`SetDataSourceMigrationWritesCommand`, audited in `AppSettingHistory` and the `MigrationWritesChanged` security event), never a host-managed or `IsReadOnly` one, checked at create, before every run and by the writer before it decrypts the destination's credentials. It writes only through the destination connector's `IMigrationBulkWriter` (an engine without one fails before decryption), on the run's one connection and one transaction — clear, primary key lookup and every chunk — so a run commits or rolls back whole (no row-by-row fallback; MySQL's implicitly committing clear excepted, §5.12); a writer never opens, commits or rolls back a connection or transaction itself. Beacon never reads a write target: `IDataSourceConnectionResolver` and the metadata scan refuse it (`MigrationWriteTargets.EnsureReadable`), and project listings MCP and AI read use `WhereReadable()` — a new read path must connect through the resolver, and a new project listing must filter (`WhereReadable()` also leaves disabled sources out). Migration reads use their own `Beacon:Migrations:MaxRows` budget and run the job's steps in-process (no query is stored to run them). A job runs once at a time: the run row is claimed in a serializable transaction (a serialization conflict is tried once more) that refuses a second run while one is starting or in progress (the response's `RunInProgress`, 409 on the route, a `run_in_progress` security event; the service does not throw) and closes Running rows older than the job's timeout plus a margin as abandoned; a run is stopped after the job's `TimeoutMinutes` (clamped to 1–1,440), its commit is never cancelled (a failed commit is recorded as `commit_unknown`, never rolled back or retried), its write holds the job's destination lock taken without waiting (`MigrationRunLock`: PostgreSQL advisory, SQL Server applock, MySQL `GET_LOCK`; busy → `destination_busy`, nothing written), and its row is always closed.

## Project authorization

§1.13 **Project access has one decider: `IProjectAccessEvaluator`.** Never re-derive it in a handler from `allowed_projects`, roles or membership rows. Every MediatR request is exactly one of: `IProjectAuthorizedRequest` (its `ProjectChecks` name every id it addresses and the `ProjectAction`; `ProjectAuthorizationBehavior` answers 404 unreadable / 403 denied before the handler), `IProjectFilteredRequest` (filters in SQL through `ProjectSet` / `ProjectAccessQueryableExtensions`, never in memory after paging), or `[ProjectScopeExempt("reason")]`, gated by the policy it names. A resource that reads several data sources is reachable only through one project that holds all of them; a query without steps only by its owner (`Query.OwnerUserId`) and Admins, and an empty source set never counts as open. Refuse with `BeaconForbiddenException` (403) / `BeaconNotFoundException` (404) through `AccessRefusal` / `ProjectAccessGuard` (ids-only security events) — never `UnauthorizedAccessException`, which the API does not map. API keys never carry the Admin bypass and are capped by the lower of their scope and their owner's global role; a session without a stored user gets nothing while user management is on. Off-request code gets the system scope only in a scope marked through `ISystemWorkScope` (a job host marks each job's scope); an unmarked scope without a request gets nothing (fail closed) and logs a warning, so every new off-request entry point marks its scope first; a path that must never run as the system (the playground) refuses explicitly. Scheduled work done for a user (subscription runs, contract evaluations, AI actor background cycles) runs as its recorded owner: the job entry point sets `IRunAsScope` before anything resolves the scope's caller, and `IExecutionAccessCheck` re-checks the exact data sources right before any SQL or LLM call; a refused run is recorded as skipped, never run as the system. MCP takes the caller's projects from the evaluator on every call (`ProjectContextFactory.PopulateAsync`, run by the MCP request filters); a null or empty project list denies, and access that could not be determined (`AccessUndetermined`) answers a retry message and fails `tools/list`, never a shorter list. New projects are restricted; the creator becomes ProjectAdmin (open only when Beacon cannot manage membership for the creator, logged as `ProjectCreatedOpen`). Check-then-write rules on memberships and links run in a serializable transaction and map serialization conflicts to 409. Users are named to other users by display name or "User {id}" (`UserLabel`), never by user name, e-mail or external id. Functional permissions (`BeaconPermissions`: Approver, Auditor, SecurityAdmin, UserAdmin, DataSourceAdmin, MigrationOperator) grant no project data: the evaluator's bypass stays bound to Admin, a duty's grant goes through `ProjectCheck.GrantedBy` or its handler (read live through `IBeaconPermissionAccessor`), and an API key never holds one. Only an Admin controls how an account signs in (creating password accounts, changing user names, e-mails or external ids); a UserAdmin cannot.

## Auth middleware

§1.8 **Cookie config:** `Beacon.Auth` cookie uses `HttpOnly = true`, `SameSite = Lax`, `SecurePolicy = SameAsRequest`. Do not weaken any of these flags. Sessions are revalidated on the server (`BeaconSessionEvents`: user store every `Session:RevalidateMinutes`, security stamp — also carried as the `BeaconClaims.SessionStamp` claim that `BeaconActorAccessor` compares on every request — and the absolute lifetime, which caps the cookie's expiry at sign-in and on every renewal; realtime hub requests are checked every time) — keep every new sign-in path going through the cookie scheme so they apply, and every change that must end a user's sessions renewing the stamp. Data Protection is the host's: `AddBeaconCookieAuthentication` configures none of it (`AddBeaconDataProtection` is the opt-in default), and outside Development a persisted key ring without `ProtectKeysWith*` fails startup (`DataProtectionKeyEncryptionCheck`). Password sign-in obeys `Beacon:UserManagement:LocalLogin` (off: the endpoint unmapped, the providers refuse, break-glass names only — exact stored user name, checked by `PasswordSignInGate` after ANY provider) at the endpoint, in `IBeaconAuthenticationService.SignInAsync` AND in the providers; never refuse a name before the password check (timing). Keys stored without encryption are revoked at startup outside Development (`DataProtectionKeyRingStartupCheck`); only `Beacon:DataProtection:AllowUnencryptedKeys` acknowledges an unencrypted ring (a Warning, never silent). `RequireMfa` covers the interactive SSO sign-in only — do not describe bearer, MCP, API-key or break-glass access as MFA-protected.

§1.9 **Middleware order is load-bearing:** `ApiKeyAuthMiddleware` → `JwtBearerAuthMiddleware` → `UseAuthentication` → `BeaconCookieAuthMiddleware` → `UseAuthorization` → `LoginFormAuthMiddleware`. `BeaconCookieAuthMiddleware` must populate `context.User` from the `Beacon.Auth` cookie BEFORE `UseAuthorization` evaluates policies, otherwise the first authorization check on a cookie session sees an unauthenticated user. It (and `ApiKeyAuthMiddleware`) record the result as the request's `IAuthenticateResultFeature` — never assign `context.User` after them, which drops the result SignalR closes hub connections by. Reordering also breaks API-key-only callers and the login redirect. `app.UseBeaconAuthentication()` wires the first four in this order — hosts call it in place of `UseAuthentication`. The Beacon middlewares (API key, bearer JWT, cookie, login form, first-run setup) scope themselves through `BeaconRequestPaths.IsBeaconRequest`: `/beacon` plus `Beacon:Authentication:AdditionalPaths` (whole-segment, case-insensitive match on `Request.Path`, so the host's `PathBase` is respected; validated at startup, `/` refused; the sample lists `/warp`). Every other request passes untouched, so a Beacon credential never authenticates a host route and a host route is never redirected to Beacon's login or setup page — keep that check first in each of them, and never add a global switch that turns it off. The cookie scheme's own events apply the same scope (`BeaconSessionEvents.ValidatePrincipalAsync` rejects the principal and `CheckSlidingExpirationAsync` refuses renewal outside it, before any user-store check and without signing out), so the `Beacon.Auth` cookie authenticates no host route even when `Cookies` is the host's default scheme or named by a host policy; keep that guard first in both events.

## SQL safety

§1.10 **Parameterize every Dapper / raw SQL query.** Never interpolate user input into SQL strings — even for column or table names, use a whitelist + parameter pattern.

## Logging

§1.11 **No PII in logs.** User-supplied query text, connection strings, full row payloads, and auth tokens NEVER reach `ILogger`. Log identifiers and counts only.
