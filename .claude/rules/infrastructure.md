# Infrastructure

> §7.x — Hosting, CI, deployment. Loaded automatically by Claude Code.

§7.1 **Hosting:** ASP.NET Core self-hosted (Kestrel) serving the React SPA at root `/` via the `Beacon.UI` Razor Class Library (Blazor/MudBlazor were removed in the Phase 3 cutover). No containerization is configured today — there is no `Dockerfile` in the repo.

§7.2 **CI/CD:** GitHub Actions. `.github/workflows/ci.yml` builds and tests every pull request and every push to `main` (read-only token, no secrets, one run per ref; same .NET/Node 22/npm 11.11.0 commands as the release, plus the web `npm ci && npm test`). `.github/workflows/w-build.yml` releases on a published release or a manual dispatch from `main`, in two jobs: `build` (`contents: read`; inputs reach scripts through `env:`, never `${{ }}` inside `run`; the version must match `^[0-9]+(\.[0-9]+){2,3}(-[0-9A-Za-z.-]+)?$` — tags look like `4.5.0.3`, no `v`; the released commit must be an ancestor of `origin/main`; restore → build → test → pack → upload the packages) and `publish` (`needs: build`, `environment: nuget-release`, the ONLY job with `id-token: write`; no checkout, no npm: download the packages, NuGet login, push). Every action in every workflow is pinned to a full commit SHA with its version in a comment — never a tag or branch.

§7.3 **NuGet publishing:** Projects with `<IsPackable>true</IsPackable>` are pushed to NuGet on release. Do not flip `IsPackable` without coordinating with the release process. Publishing is trusted publishing (OIDC, short-lived key, `--skip-duplicate`), and the nuget.org policy binds the workflow file name — keep `w-build.yml`. A push waits for approval in the `nuget-release` environment (its reviewers and deployment rules are repository settings). Any change to the release triggers, permissions or environment needs the user's explicit OK before merge, and nothing an agent runs may trigger, dispatch or publish a release.

§7.4 **Background jobs:** Moberg.Warp backed by PostgreSQL (dedicated `WarpDbContext`, `warp` schema). Dashboard mounts at `/warp` (admin-only, via `WarpDashboardAuthFilter : IWarpAuthorizationFilter`). `LoginFormAuthMiddleware` leaves the `/warp` prefix (exact case) to the dashboard's own check. Warp replaced Hangfire.

§7.5 **MCP server:** Streamable HTTP transport, mounted at `/beacon/mcp` via `ModelContextProtocol.AspNetCore`. Wired with `app.MapBeaconMcp()` (in `Beacon.MCP`), which maps `/beacon/mcp` with the Execute-scope policy — the Execute scope is load-bearing (§1.4: `ask`/`query` execute SQL, so a Read-scoped API key must not reach MCP). Inside the MCP layer `McpScopeMessageFilter` (incoming message filter: every request but `initialize`/`ping`/`tools/call`) and `McpScopeCallToolFilter` (registered first; audits the refusal) refuse scoped callers without Execute and unauthenticated HTTP callers, so a host mapping the route with a weaker policy still fails closed. Do not move the route, map it with `MapMcp(...)` and bare `RequireAuthorization()`, or remove the auth requirement or the filters.

§7.7 **MCP discovery documents** are mapped by `app.MapMcpDiscovery()` and are anonymous BY DESIGN: `/.well-known/oauth-protected-resource`, its `/beacon/mcp` path-inserted variant, and `/.well-known/mcp/server-card.json`. `Beacon.Core.Mcp.McpDiscoveryPaths.AnonymousDiscoveryPaths` is the single source of truth — the routes are mapped from it (`.AllowAnonymous()`, which `LoginFormAuthMiddleware` honours only at the exact, Ordinal path) and `FirstRunSetupMiddleware` derives its allow-list from it. It lives in Core (not MCP) because the middlewares ship in `Beacon.Api`, and Api must not reference the sibling `Beacon.MCP` (§2.4); `McpDiscoveryEndpoints.AnonymousDiscoveryPaths` and `McpDiscoveryDocuments`' path constants are forwarding aliases — do NOT re-declare these paths anywhere. NEVER allow-list `/.well-known` as a prefix; match those exact paths only. Set `Beacon:PublicBaseUrl` in any proxied deployment, or the documents reflect the client-controlled Host header (the host logs a startup warning when it is unset).

§7.6 **Composition root** is `Beacon.SampleProject` (yes, the name is historical). All cross-project DI registration, configuration loading, and Warp setup (`AddDbContext<WarpDbContext>` + `AddWarpServer` + `UseWarpUI`) live in `src/Beacon.SampleProject/Program.cs`.
